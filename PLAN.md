# PCGExAssistant : Plan

> AI agent integration for the PCGEx ecosystem. One companion plugin, one data pipeline, no bespoke protocol code. Written 2026-08-30 against UE 5.8; the engine surface this builds on is experimental and every finding below should be re-verified on the next engine version.

## The core insight

UE 5.8 ships an experimental three-layer AI stack, and the middle layer is the only integration point we need:

```
consumers      Epic AI Assistant (in-editor)        External MCP clients (Claude Code, Cursor, ...)
                       |                                        |
                       |                     Engine "Unreal MCP" server (ModelContextProtocol plugin)
                       |                                        |
registry       ToolsetRegistry  <--  one registration call, everything above is free
                       |
providers      PCGToolset (Epic, PCG graph surgery)   PCGExAssistant (us)   ~20 other Epic toolsets
```

We register a **toolset**: a `UToolsetDefinition` subclass whose tools are static `UFUNCTION(meta = (AICallable))` functions. The engine derives tool names, descriptions and JSON schemas from reflection and doc comments. Both Epic's in-editor assistant and any external MCP client connected to the engine's MCP server can then call us. We write zero protocol code, zero server code, zero client config code (the engine even writes `.mcp.json` for Claude Code via `WriteClientConfiguration`).

Equally important: **Epic's own `PCGToolset` already does generic PCG graph surgery** (`CreateGraph`, `AddNode`, `UpdateNode`, `ConnectNodePins`, `GetNativeNodeSchema`, `GetNodeDataView`, ...), and PCGEx nodes are PCG nodes. We never duplicate that. Our value is what Epic cannot have:

1. **Knowledge.** The documentation card store: purpose, mechanism, exact pin contracts, settings semantics with traps, per node, for hundreds of PCGEx nodes, verified against source.
2. **PCGEx idioms.** Multi-node patterns generic surgery cannot know: subnode/factory chains, filter ensembles, cluster pipelines, staging flows.

## Phases

### Phase 0 : Knowledge bundle (documentation repo)

A `render-bundle` sibling to `render-cards.js` in the GitBook automation pipeline. Flattens index + cards into one queryable JSON dataset per plugin: node id, display name, classification, purpose + canonical situation (the search surface), mechanism, pin contract, settings (type, tooltip, semantics, traps, enums), related pages.

- Published to its **own public repository** so third parties can build their own tooling on the raw data.
- A copy ships in this plugin's `Knowledge/` folder, so knowledge always matches the installed plugin versions (cards are stamped against `source_hash`; the bundle inherits that guarantee).
- Regenerated by the same automation that renders the book: zero marginal authoring cost.

### Phase 1 : Knowledge tools

`SearchNodes` / `GetNode` served from `Knowledge/`. Tiered by design: search returns id + name + one-liner; the full card comes only on request. This mirrors the engine MCP server's own tool-search mode (three meta-tools, `list_toolsets` / `describe_toolset` / `call_tool`), where breadth is nearly free but the **toolset-level description carries everything**: it is the only text the model sees when deciding whether to look at us at all. The `UCLASS` doc comment on `UPCGExToolset` is that description; treat it as the highest-leverage prose in the plugin, and state anti-scope ("NOT for stock PCG questions") the way Epic's `Skill_PCGGraphGeneration` does.

Also in this phase: a standalone stdio MCP server (npx-able) over the same bundle for use **outside** the editor. Optional, cheap, same data.

### Phase 2 : Editor introspection

Read-only tools grounding advice in the user's actual session:

- `GetInstalledPCGExPlugins` (implemented): names + versions of the PCGEx family.
- `ListRegisteredNodeTypes` (stub): live reflection over `UPCGSettings`-derived classes from PCGEx modules. Display names, never class names (`FindContours` renders as "Find Cells"; class names have produced fabricated docs before).
- Later candidates: summarize the PCGEx content of the focused graph (Epic's assistant exposes the focused asset via `UAIAssistantToolset::GetDockedContext`, so the model can combine the two).

**Agent Skills** land here too. A skill is a `UAgentSkill` Blueprint asset (short `Description` for the catalog + long `Instructions` prose), auto-discovered from `Content/Skills/` via the asset registry, no registration call. Concept-level documentation (clusters, filter ensembles, staging, tensors) fits skills better than tool calls. Rules learned from Epic's eight PCG skills: one skill per *task the agent performs*, not per documentation page; ~20 KB each; descriptions must state scope and anti-scope; empty description = invisible; a `GeneratePrompt` override can template live editor state (e.g. the installed node list) into the prose at read time. The Python authoring route (`@agent_skill` decorator) can generate skills from the card corpus mechanically; note Python-defined skills are transient and read-only to the agent, which is exactly right for docs.

### Phase 3 : Actuation (scaffold only)

`AddSubnodeChain` stands as the marker: build a filter/heuristic/tensor subnode chain feeding a target node in one call, wired the way PCGEx expects. More idioms only if Phases 1-2 show models failing at multi-node composition through Epic's generic tools. Rules when this becomes real:

- Wrap mutations in `GEditor->BeginTransaction` / `EndTransaction`; the assistant's per-conversation undo buffer is **off by default**.
- Report failures with `UKismetSystemLibrary::RaiseScriptError(...)` on the game thread (tool calls always arrive on the game thread).
- Long/interactive operations return a `UToolCallAsyncResult` subclass.
- If PCGEx selector-like types need terse string forms, implement a `FToolsetJsonConverter` and `RegisterConverter` (Epic does this for `FPCGAttributePropertySelector`).
- Consider a `UDeveloperSettings` with `TArray<FDirectoryPath>` so users can register their own example graphs into the assistant's vocabulary (Epic's `PCGToolsetSettings` pattern).

## Contract notes (verified in 5.8 source)

- Registration: `UToolsetRegistry::RegisterToolsetClass(UPCGExToolset::StaticClass())` from `StartupModule()`; unregister on shutdown. Module loads at `PostEngineInit` (all Epic toolsets do; the registry subsystem must exist first).
- Toolset name is **derived**, not chosen: `<module package>.<class>` -> `PCGExAssistant.PCGExToolset`. Users gate toolsets by name substring in Project Settings > Toolset Registry, so the `PCGEx` prefix makes the whole surface allow/blockable in one entry.
- Every `UFUNCTION` on the class must be static + `AICallable`, or carry `AIIgnore`; anything else logs errors. A class yielding zero valid tools is **silently refused** (warning in `LogToolsetRegistry`).
- Doc comments are the prompt: function tooltip = tool description, `@param` = parameter descriptions, C++ defaults = schema defaults.
- `ToolsetRegistry`, `ModelContextProtocol` and `AIAssistant` are `NoRedist` + experimental. They ship in launcher builds but Epic can reshape or remove them. This plugin declares the `ToolsetRegistry` dependency in its `.uplugin`, so without that engine plugin ours simply cannot be enabled; the main toolkit never takes the dependency.
- End-user wiring for Claude Code: enable `ModelContextProtocol`, Editor Preferences > Model Context Protocol (port, auto-start), let it write `.mcp.json`. We should document this as a one-page setup guide and possibly surface a "write client config" button, but we build none of it.

## Open questions

- Bundle repo name and layout (per-plugin JSON files vs one merged dataset; include concept-page prose or nodes only).
- Skill set v1: which concept docs become skills, and whether they are generated (Python route) or authored (Blueprint assets).
- Whether the out-of-editor stdio MCP server is worth shipping v1 or waits for demand.
- UE version gating: this targets 5.8's experimental surface; decide policy when 5.9 moves it.
